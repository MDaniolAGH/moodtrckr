# Testable requirements

A requirement is a need the client agreed to, written so that anyone can check whether it is met.

## Principles

- **Problem before solution.** Start from the need ("participants complete the entry without
  help"), not the idea ("bigger icons"). Ideas stay ideas until the client approves them.
- **Testable.** Each requirement has acceptance criteria someone can verify with synthetic data.
- **Traceable.** Each requirement points to its source: brief, client answer, stakeholder,
  observation. No source, no requirement.
- **Small scope.** Prioritise; "Won't (this time)" is a valid and useful answer.

## Steps

1. Collect needs from the brief, answers, stakeholder map and app observations.
2. Write each as: *"[Who] can/must [do or get what], so that [goal]."*
3. Add 1–3 acceptance criteria: *Given [context], when [action], then [observable result].*
4. Add source and priority (Must / Should / Could / Won't).
5. Move solution ideas and anything without a source to a separate "Ideas" list.

## Output

| ID | Requirement | Acceptance criteria | Source | Priority |
|----|-------------|---------------------|--------|----------|

Ideas (not approved): <list>

Write the output in the language of the client brief.

## Done when

- Every Must has acceptance criteria and a source.
- No requirement names a UI element, technology or vendor unless the client required it.
